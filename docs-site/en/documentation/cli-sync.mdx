# Kest Cloud Sync

Kest Cloud Sync connects the local CLI, Web workspace, and CI into the same Cloud workspace. After syncing, your team can review API specs, request history, flow definitions, flow run results, and CI status in Kest Web.

For the full Web console surface, see [Kest Web / Cloud](/en/documentation/kest-web-cloud). For local command-line usage, see [Kest CLI](/en/documentation/kest-cli).

## What Syncs

Cloud Sync covers four data types:

- API specs: the CLI infers API specs from local request history and uploads them into the workspace.
- Request history: the CLI syncs local requests, responses, durations, statuses, and errors into workspace history.
- Flows: the CLI syncs local `.flow.md` definitions into workspace flows, and can also pull runnable flows from Cloud for local execution.
- Flow runs / CI runs: the CLI or CI syncs flow run results, step results, log excerpts, and runner type back to Cloud.

## Prerequisites

You need:

- A Kest Cloud account.
- A Cloud workspace.
- Kest CLI installed locally.
- A workspace CLI key or workspace-scoped CLI token.

Install the CLI:

```bash
curl -fsSL https://kest.dev/install.sh | sh
```

Initialize local Kest files:

```bash
kest init
```

## Recommended Connection Flow

The simplest connection path is to copy the one-line command from the workspace Keys page in Web.

```bash
kest key kest_key_...
```

`kest key` writes the connection details into `.kest/config.yaml`:

```yaml
platform_url: https://api.kest.dev/v1
platform_token: kest_pat_...
platform_workspace_id: "workspace-id"
platform_auto_sync_history: true
```

The connection key is a one-time configuration carrier generated by Web. It is not a raw CLI token. Raw CLI tokens usually start with `kest_pat_` and should only be used as automation environment variables or config values.

## Manual Configuration

If you do not use the one-line connection key, configure Cloud manually:

```bash
kest sync config \
  --platform-url https://api.kest.dev/v1 \
  --platform-token kest_pat_... \
  --workspace-id <workspace-id> \
  --auto-sync-history
```

You can also write individual config values with `kest config set`:

```bash
kest config set platform_url https://api.kest.dev/v1
kest config set platform_token kest_pat_...
kest config set platform_workspace_id <workspace-id>
kest config set platform_auto_sync_history true
```

View the current config:

```bash
kest config list
```

## CLI Token Scopes

Workspace CLI tokens support these scopes:

- `collection:read`: upload API specs inferred from local history.
- `collection:run`: upload CLI request history.
- `environment:read`: read workspace environment data.
- `test_case:run`: run test cases.
- `flow:run`: pull runnable flows, upload flow run results, and send CI webhooks.
- `flow:write`: upload or update flow definitions.

When Web generates a token without explicit scopes, Kest uses default scopes that cover the common sync capabilities above.

## Sync API Specs

`kest sync push` analyzes local request history and converts real method, path, headers, request body, responses, and examples into API specs.

Preview what will sync:

```bash
kest sync push --dry-run
```

Upload after review:

```bash
kest sync push
```

Specify a workspace:

```bash
kest sync push --workspace-id <workspace-id>
```

Temporarily override the Cloud URL or token:

```bash
kest sync push \
  --api-url https://api.kest.dev/v1 \
  --token kest_pat_...
```

Cloud endpoint:

```text
POST /workspaces/{workspaceId}/cli/spec-sync
```

## Sync Request History

Manually upload local CLI request history for the current local scope:

```bash
kest sync history
```

Limit the number of records:

```bash
kest sync history --limit 1000
```

Only sync records from the last 24 hours:

```bash
kest sync history --since 24h
```

Preview without uploading:

```bash
kest sync history --dry-run
```

Sync across all local Kest workspaces:

```bash
kest sync history --all
```

Cloud endpoint:

```text
POST /workspaces/{workspaceId}/cli/history-sync
```

When `platform_auto_sync_history` is `true`, the CLI tries to flush the local outbox while running requests and flows. If the network is unavailable, records remain local and later commands continue syncing.

## Sync Flow Definitions and Run Results

Run a local flow and sync its definition and result:

```bash
kest run auth.flow.md --sync
```

Use a profile:

```bash
kest run --profile local --sync
```

Set the runner type:

```bash
kest run --profile ci --sync --runner-type server_ci
```

Common runner types:

- `test_machine`: run from a developer machine or test machine.
- `server_ci`: run from CI or server automation.

Cloud endpoints:

```text
POST /workspaces/{workspaceId}/cli/flows/sync
POST /workspaces/{workspaceId}/cli/flow-runs/sync
```

## Pull Runnable Flows from Cloud

Flows that are enabled and parsed successfully in Web can be pulled down and executed by the CLI.

Run all runnable flows:

```bash
kest run --workspace-flow all --sync
```

Run one flow by flow ID, source ID, or source path:

```bash
kest run --workspace-flow <flow-id> --sync
kest run --workspace-flow .kest/flow/auth/login.flow.md --sync
```

Cloud endpoint:

```text
GET /workspaces/{workspaceId}/cli/flows/runnable
```

This mode is useful when a team manages flow content in Web and lets local machines or CI pull it for execution.

## CI Sync

CI can reuse the same `.flow.md` files and sync results back to Cloud.

Recommended command:

```bash
kest run --profile ci --sync --quiet --output json
```

Generate JSON and JUnit reports:

```bash
kest run --profile ci \
  --sync \
  --runner-type server_ci \
  --report-json .kest/reports/flow-results.json \
  --report-junit .kest/reports/flow-results.xml
```

Common CI environment variables:

```bash
export KEST_BASE_URL="https://staging.example.com"
export KEST_PROFILE="ci"
export KEST_SYNC_FLOWS="1"
export KEST_CLI_BIN="./.bin/kest"
```

Cloud also exposes a CI webhook endpoint:

```text
POST /workspaces/{workspaceId}/cli/ci/webhook
```

Web can use this endpoint to generate a CI-ready `kest run --workspace-flow all --runner-type server_ci --sync` command.

## Flow Profile Configuration

`kest init` creates `.kest/flow.config.yaml`. A typical CI profile enables strict mode, sync, and report outputs:

```yaml
profiles:
  ci:
    include:
      - ".kest/flow/**/*.flow.md"
    env: staging
    strict: true
    fail_fast: false
    sync: true
    reports:
      json: ".kest/reports/flow-results.json"
      junit: ".kest/reports/flow-results.xml"
```

Run it:

```bash
kest run --profile ci
```

Or select the profile with an environment variable:

```bash
KEST_PROFILE=ci kest run
```

## Security Behavior

Cloud Sync is designed to avoid storing sensitive data directly in Cloud:

- CLI tokens are stored as hashes and raw tokens are only shown at creation time.
- Request history and examples are sanitized for common secret headers and body fields.
- Long bodies, responses, and logs are truncated.
- Sync endpoints use workspace-scoped CLI tokens and should not use browser login JWTs.
- Token scopes should be minimized for each automation task.

## Troubleshooting

Check whether config is complete:

```bash
kest config list
```

Verify the workspace ID:

```bash
kest sync push --workspace-id <workspace-id> --dry-run
```

If a token is missing scopes, generate a new key from the workspace Keys page in Web and reconnect:

```bash
kest key kest_key_...
```

If automatic history sync fails, retry manually:

```bash
kest sync history --since 24h
```

If CI runs but Cloud does not show results, confirm the command includes:

```bash
--sync --runner-type server_ci
```

Also confirm the CI environment has a valid Cloud token and workspace ID config.
