# Flow Authoring Reference

Kest flows are Markdown files ending in `.flow.md`. They describe API workflows in text that can be reviewed by humans, run by the CLI, and synced to Kest Cloud.

## File Structure

A flow file can contain:

- `flow` metadata.
- `setup` blocks.
- `step` blocks.
- `edge` blocks.
- `teardown` blocks.

````md
# Auth smoke test

```flow
@flow id=auth-smoke
@name Auth smoke test
@version 1.0.0
@env staging
@tags smoke,auth
```

```step
@id login
@name Login
@type http
@retry 2

POST {{base_url}}/v1/login
Content-Type: application/json

{
  "email": "{{email}}",
  "password": "{{password}}"
}

[Captures]
token = body.access_token

[Asserts]
status == 200
body.access_token exists
```

```step
@id profile
@name Fetch profile
@type http

GET {{base_url}}/v1/users/profile
Authorization: Bearer {{token}}

[Asserts]
status == 200
```

````

Steps run top to bottom, so this flow needs no `edge` blocks.

## Flow Metadata

Use the `flow` block for stable identity and labels:

~~~md
```flow
@flow id=checkout-smoke
@name Checkout smoke
@version 1.0.0
@env staging
@tags checkout,smoke
```
~~~

The `id` should stay stable across file moves so Cloud can track revisions and run history.

## HTTP Steps

HTTP steps describe a request and optional captures/assertions:

~~~md
```step
@id create-user
@name Create user
@type http
@retry 2
@retry-wait 500ms
@timeout 10s

POST {{base_url}}/v1/users
Content-Type: application/json

{
  "email": "{{$randomEmail}}"
}

[Captures]
user_id = body.id

[Asserts]
status == 201
duration < 1000
```
~~~

Common step directives:

- `@id`: stable step ID.
- `@name`: display name.
- `@type`: `http` or `exec`.
- `@retry`: retry count.
- `@retry-wait`: wait between retries.
- `@timeout` or `@max-duration`: execution timeout.
- `@wait`: wait before running the step.

## Exec Steps

Exec steps run local shell commands:

~~~md
```step
@id seed-user
@name Seed user
@type exec
@timeout 30s

echo '{"email":"seed@example.com"}'

[Captures]
seed_email = stdout.email
```
~~~

Use exec steps for local setup, fixture creation, or tooling that is already present in the CI environment.

## Edges

Edges are optional. Without edges, steps run in file order, which is identical to a flow that has a `@on success` edge between every pair of neighbouring steps, so you do not need to write those (`kest lint` reports them as `redundant-edge`).

Use an edge only for non-linear order, for example to run a step before a step declared above it:

~~~md
```edge
@from login
@to profile
@on success
```
~~~

Edges order the `step` blocks with a topological sort; steps no edge relates keep file order. `@on` is a label only. If edges reference unknown steps or form a cycle, the file falls back to file order. `setup` and `teardown` blocks are never reordered.

## Flow-level Defaults

Declare defaults once in the `flow` block instead of repeating them in every step:

~~~md
```flow
@flow id=orders
@default-header Accept: application/json
@default-assert status == 200
@auto-content-type json
```
~~~

- `@default-header Name: value` is added to every HTTP step unless the step sets the same header.
- `@default-assert expr` is added to every HTTP step unless the step already asserts the same subject (for example a step with its own `status == 201` skips the default `status == 200`).
- `@auto-content-type json` sends `Content-Type: application/json` for JSON bodies that have no `Content-Type` header. Without this opt-in Kest never adds one.
- Put `@no-defaults` in a step to skip all of the above for that step.

Default assertions are evaluated like any other assertion, so they appear in the run output, JSON, and HTML report.

## Reusing Steps with `@use`

Share a login (or any setup) across files:

~~~md
```flow
@flow id=orders
@use ./common/login.flow.md
@use ./common/seed.flow.md as seed
```
~~~

The included file's `setup` and `step` blocks run first, in the setup phase, before this file's own steps. Captured variables are shared (`{{token}}` stays `{{token}}`), but step ids are namespaced (`login.step-id`, or `seed.step-id` with `as seed`) so they never collide. Paths are relative to the including file. Missing files and include cycles are reported with the line of the `@use`.

## Secrets

Do not commit credentials. Use `"password": "{{$env.ADMIN_PASSWORD}}"`: `$env.NAME` reads the OS environment first, then `.kest/.env`. `kest lint` flags literal secrets (`inline-secret`).

## Setup and Teardown

Use setup for prerequisites and teardown for cleanup:

~~~md
```setup
@id prepare
@type exec

echo "prepare test data"
```

```teardown
@id cleanup
@type exec

echo "cleanup test data"
```
~~~

## Profiles

`.kest/flow.config.yaml` controls default targets and run behavior:

```yaml
profiles:
  local:
    include:
      - ".kest/flow/**/*.flow.md"
    env: local
    strict: true
    fail_fast: false

  ci:
    include:
      - ".kest/flow/**/*.flow.md"
    env: staging
    strict: true
    sync: true
```

Run a profile:

```bash
kest run --profile ci
```

Override the base URL for one run:

```bash
kest run --profile ci --base-url https://staging.example.com
```
